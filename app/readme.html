Overview

Import Microsoft Defender quarantined email into Splunk SOAR or Enterprise Security through Azure Automation. Each message includes its original email, attachments and selected metadata. Importing a message does not release or deny it.

This distribution has its own app UUID and package identity. It does not convert assets belonging to another app. Configure one ingesting asset per tenant; pause previous intake before a controlled replacement.

Requirements and setup

  1. Deploy the companion Azure Automation Runbook 1.0.0 separately. Enable the Automation Account's system-assigned Managed Identity and install the ExchangeOnlineManagement module in its PowerShell runtime.
  2. Grant the Managed Identity Exchange.ManageAsApp and the Exchange/Defender permissions for the quarantine actions you intend to use. Exchange sign-in uses Managed Identity, not the asset's client secret.
  3. Create a runbook webhook. Enter its direct HTTPS URL and the Automation Account coordinates in the asset. Configure a separate App Registration with Automation Job Operator access on that account for reading Azure job status and output. Enter its tenant ID, client ID and client secret value.
  4. Set the Exchange tenant domain in the asset or in the Automation Variable ExchangeOrganization; the asset value takes precedence.
  5. Use one ingesting asset per tenant. Select the target before starting Requested-only intake. Configure the container label and schedule in Ingest Settings; disable the schedule to pause automatic imports. Use Poll Now for a manual import. For ES, use the native ES ingest settings below.
  6. Configure the analysis playbook's asset bindings, analyst/approver settings, notification recipients, portal links and routing label before activation. Publish and confirm the matching runbook first, install the matching app, then activate its compatible playbook. For combined-layout SOAR, start analysis from the completed mail's single email artifact.

Native email import requires authenticated local SOAR REST access, including when importing into SOAR rather than ES. Automation Broker is not supported. The manifest minimum is SOAR 8.5.0 with Python 3.9/3.13 runtimes; use the runtime supported by your platform. SOAR 8.7 and later use Python 3.13.

Email import

on_poll_max_containers is a maximum of simultaneously unresolved Microsoft quarantine identities, configurable 1–50 and default 10. It is not a per-poll increment. The app checks tracked IDs read-only; exact Released or Denied frees slots. It fills free slots from the first 50 candidates with status Requested. Missing IDs, errors, other statuses and analysis completion do not free slots. An empty import does not prove an empty backlog; no pagination or stable ordering is promised.

Intake imports only Microsoft Requested messages: mail with a recipient release request. There is no source-mode selector; obsolete asset settings are ignored. Existing intake scopes containing needs_review are normalized without deleting records or changing tenant/organization/target scope. Published references are retained and successful imports are not republished. Older pending or unconfirmed attempts are not automatically replayed. They require a deliberate Poll Now retry and must appear as Requested in the first 50 candidates. Microsoft-status checks continue for tracked identities. A mail left unchanged can occupy a slot indefinitely. Failed imports also hold their slot; retrying one does not consume an additional slot.

SOAR events

New SOAR events are named after the email subject, without a prefix; mail without a subject uses [No subject].

Original email and attachments are saved automatically to the container's Vault. In the combined SOAR layout, exactly one email artifact is saved last, after all uploads, with native run_automation=true outside CEF. Its vaultId always references the original EML; senderAddress and recipientAddress always come from Microsoft's quarantine-list values, not RFC Sender or delivery headers. These fields have no selection controls; old false settings cannot suppress them. Existing optional selections extend the same artifact; unavailable optional headers are omitted. With all optional fields off, the three required fields still produce one usable artifact.

The email artifact is named after the email subject (No subject if absent). Read identity from container:data.quarantine_identity and subject from container:name. No separate Request, Original-EML, Ready, technical or attachment email artifacts are created in this layout, and no ingestionReady flag is required. Vault files and platform file metadata remain available. Historical events are not rewritten.

Update existing playbooks that require Ready/Request artifacts together with the producer before activation: remove those readiness/correlation gates and map analyzers directly to the single artifact's vaultId, Release/Deny to the event identity, and prompt context to the fields above. Preserve decisions, approvals and other business flow. These consumer mappings are unchanged by the import/disposition simplification. This app does not update or activate playbooks.

The separate-field SOAR layout retains its existing behavior. Internal EML export and chunked transport are unchanged. Separate layout still uses a final Ready artifact; legacy stored field selections remain readable. ES uses its configured native threat-analysis and automation settings unchanged. Publication acceptance does not prove that an analysis workflow finished.

Native ES prerequisites

No custom ES fields are required. For Release/Deny use container:data.quarantine_identity from the linked SOAR container. Configure a valid security domain; urgency and investigation type are optional native settings. Analyst download links use the validated external HTTPS base URL from SOAR system information. Test their reachability and mail/attachment rendering from the analyst interface. ES is a lossy projection: the outer message body prefers plain text, then HTML; attachment-marked parts, file-named parts and attached-message descendants are excluded. Related MIME uses its declared root (or first part). Header values are limited to 8192 characters and body to 256000 characters. The 2 MiB metadata check precedes attachment-link entries and is not a complete final-request size guarantee. The original EML in Vault remains authoritative.

Configure the Azure connection, active-message limit, selected mail fields and advanced job settings below. The ingest schedule is set in SOAR/ES Ingest Settings; the Azure polling interval and timeout monitor individual Azure jobs, not the mail-import schedule.

The SOAR URL override applies to both SOAR and ES email import. Azure connections require HTTPS and certificate verification; webhook redirects are not followed. Configure the platform's trusted CA store for private certificates.

Available actions

Release and Deny run only when invoked by an operator or playbook. The app submits one Azure job, waits for its output and returns a native ActionResult. The runbook checks the exact identity and requires Microsoft Requested or an already matching terminal status. Release uses Release-QuarantineMessage -Identity <id> -ReleaseToAll -Confirm:$false -ErrorAction Stop; Deny adds -ActionType Deny to that same command. No extra configuration-check job or diagnostic proof is required before normal actions.

After a successful command, the runbook allows up to seven status reads, ten seconds apart, for Exchange to report Released or Denied. A command error remains an error; later status reads do not reconstruct success. The default Azure job/output wait remains 600 seconds with 5-second status polling. Existing whole-second ranges are 600–3600 for timeout and 1–60 for polling. Transient reads can retry within one deadline, respecting Retry-After; the writing webhook is never automatically retried.

Maintenance and removal

Back up the app, asset configuration and app state using the platform backup procedure. Stop ingestion and dependent automation before removing the app. Inspect unresolved job and import outcomes before restoring a backup; do not clear state to restart processing. Preserve the existing ingest scope and native references. An upgrade does not automatically replay older pending work.

Failures and deliberate retries

Import is synchronous: export mail, prepare container and files, then publish complete input. A small identity/result record retains the outcome and native references; there is no background recovery workflow. Scheduled polls skip failed or interrupted identities. A failed import is not a successful import.

Inspect the action error and any existing native container, Vault files, final email artifact (Ready artifact in separate layout) or ES finding. Correct the reported problem, then use native Poll Now for a fresh attempt of failed identities still present in the first 50 Requested candidates. There is no new retry parameter. Poll Now can also admit new messages within its normal count and active-message limit. Successful retained identities remain deduplicated, and a newly failed attempt is not retried again within that poll.

Native container, Vault, artifact and ES calls are not one exactly-once transaction. If an ES response is lost, a finding may already exist; a fresh attempt can duplicate it. Inspect native evidence before deciding to retry.

For Release/Deny failures, read the actual Azure/Exchange error and known azure_job_id in the native ActionResult. A timeout means the result is unknown; it does not cancel Azure. Inspect the original job and output in Azure Automation. If the webhook response was lost without a job ID, inspect Azure job history before a new action. Do not infer a root cause from missing output. The app does not automatically replay or resume the action.

A consciously started new disposition is allowed after an old uncertainty; there is no persistent disposition registry or manual operation ID. Each new action performs fresh validation. Use inspect release environment for optional read-only identity/runtime diagnosis; enable its optional RBAC inspection only when needed, not as a normal business prerequisite.

Limits and data handling

EML cap: 24 MiB. MIME limits: 200 parts, nesting depth 30, 100 attachments, 48 MiB combined decoded attachments. Import record cap: 1000 records; active items are not evicted. Terminal retention is configurable 1–365 days, default 30. Retention expiry can allow reappearing source records to be admitted again; there is no global exactly-once guarantee. Scheduled polls use a 600-second between-call work budget. Poll Now always checks tracked statuses before intake, even with a paused schedule: status checks and imports each receive a separate 600-second work budget. This is not a ten-minute total action timeout; one in-flight operation may run longer than its phase budget. Failed attempts still require deliberate Poll Now, not a later scheduled retry.

Mail and attachments may contain sensitive content or malware. Original mail travels from Exchange through Azure Automation to SOAR/Vault; ES receives finding metadata and mail/file links. Apply platform permissions, retention and handling policies to jobs, Vault, state and evidence. No credentials are stored in this help. Do not include message bodies, tokens or webhook URLs in support reports.

Troubleshooting and support

If an action fails, record the app and runbook versions, SOAR/ES versions, actual action error and known Azure job ID. Check the job output and, if needed, use optional manual inspection for the current Microsoft status. A successful local test or publication receipt does not establish downstream execution or customer production acceptance. Do not include client secrets, webhook tokens or message contents in support reports.
